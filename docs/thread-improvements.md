## 验收原则

- 建议未确认不创建支线；刷新、双击或网络重试不能重复交办；不能篡改标题/任务或跨空间确认。
- 并发以实际运行中的生成任务计数，同一支线不在数据库与内存重复计数；失败或停止后唤醒排队任务。
- 用量只展示供应商回报的 token，不将缓存 token 再加进输入；明确统计口径和缺失情况。
- 工具完成和工具意图分开记录；在外部副作用与数据库写入之间中断时无法保证 exactly-once，禁止自动重放写操作。

## 实现与接口

### 1. 空间并发

`ChatService` 对主线交办的支线使用 2 个执行槽位，已排队输入保存在 SQLite。任务结束、失败或停止后按空间扫描待投递输入，填满可用槽位。统计不再把数据库和内存中的同一次生成算两遍。直接向支线发送或重新生成时，如没有空闲槽位返回 409（输入保留，稍后重试）；不会借此绕过限制。纯排队任务也可通过原 stop 接口取消。

这是**单后端进程**的限制，不是跨多个 uvicorn worker 的分布式调度。学情分析/后台笔记仍有自己的调用，槽位不是供应商级的全局请求限速。

### 2. 建议卡片

- `propose_threads(proposals[])`：每次 1–4 项，每项 `title/task/reason`；一条回复最多 8 项。
- 模型询问学习路线时提议；用户明确要求开始任务时仍可直接 `dispatch_thread`，具体补充续接已有支线。
- `ChatMessage.thread_proposals`：返回服务端生成的 `id`、内容及已确认的 `thread_id`。
- `POST /api/conversations/{main_id}/confirm-proposal`，只接收 `{message_id, proposal_id}`。
- 确认时读取服务器保存的内容和原始 `reply_to`，不能用最新提问替换来源；幂等键包含 proposal ID。刷新后保留确认状态；前端提供开启、查看、失败重试。

### 3. 用量

- Chat Completions 请求标准 `stream_options.include_usage=true`，解析普通 JSON 或 SSE 的 usage（包括 `choices: []` 的尾块）。服务端需要支持这一标准参数。
- `model_usage` 按供应商请求记录用量；同一请求重复出现 usage 只更新、不累加。工具后的再次模型请求分别记账。
- 学情分析、后台笔记与合并小结的请求也记账；重新生成删除旧回复不会删除已发生的请求消耗。
- `GET /api/subjects/{subject_id}/usage` 返回 total 和 conversations；`GET /api/conversations/{id}/usage` 返回单会话汇总。空间总用量含主线和支线。
- 支持 OpenAI `prompt_tokens_details.cached_tokens` 和 DeepSeek `prompt_cache_hit_tokens`；缓存属于输入子集。供应商未回报则显示“未回报”，并给出已回报/总请求数。旧历史不补估、无价格估算、不承诺与完整账单相等。

### 4. 安全恢复

- 工具调用前持久化整个批次；每个工具执行前保存 `in_flight`，执行后保存结果与 `next_call`。消息 meta 中的 `last_checkpoint` 保存完成轮数、模型消息、已完成工具结果和工作区路径。
- `ChatMessage.checkpoint_available`、`checkpoint_blocked_reason` 驱动前端的“从断点继续”和风险说明。
- `POST /api/conversations/{thread_id}/messages/{message_id}/resume`：显式继续失败回复，仍用原回复 ID，后台执行，受并发槽位约束。校验所属会话、最新轮次和工作区未改变。
- 已完成工具不重放；等待审批但尚未执行的工具重新询问。执行结果不确定时，只允许重复只读工具（read/session_search/exercise_reference），写文件、命令及其他潜在副作用工具禁止自动重放。
- 恢复模型生成时舍弃没有完成的那一小段流式文本，从最近的完整工具断点接续，避免拼接出重复或残缺回答。成功后释放断点数据。
- 重启不会盲目自动恢复失败的写操作；仍自动投递尚未执行的交办任务。主动停止的 cancelled 回复不提供自动恢复。

人工验收建议：

1. 在学习空间主线问“我该怎么学”，应显示建议且未创建支线；确认一项后开始执行，刷新后按钮变成“已开启 · 查看”。实际模型的提议策略仍需验收。
2. 一次交办 4 个独立任务，观察 2 个执行、2 个排队；停止或完成前面的任务，后续自动接上。
3. 展开空间/支线的“用量”，检查请求覆盖数和缓存说明；服务未回报时不能显示虚构 token 或费用。
4. 通过测试脚本的隔离数据库验收崩溃恢复；不要为了测试未知副作用而中断真实文件操作。
5. 同一支线连续聊多轮，主线消息数不变；每条被交办的用户消息下只有一张支线卡，状态点随支线实时变化（见 [待解决问题清单 · 问题一](pending-work.md)）。
