# 记忆治理 v2 任务书（2026-11-04）

> 交给 Cursor 并行执行。共 A、B、C 三份任务：A 和 B 完全独立；C 依赖 A 定义的字段，但可以同时开工（字段按可选处理）。
> 背景见 [记忆治理优化.md](记忆治理优化.md)（v1，参照 Hermes 做的笔记条目化、快照、复盘、审批）和 GitHub issue #19。

## 为什么要改

产品核心是「AI 了解用户」：学习能力、学习偏好、兴趣、进度，并据此调整讲法。现在有两条规则把这件事堵住了：

1. **学习观察必须有原话证据。** `validate_analysis`（`backend/app/chat/agent.py`）要求证据逐字出现在用户最新消息里，否则整条丢弃。用户不会亲口说「我递归边界老出错」「我看例子学得快」，这类从行为里看出来的东西因此全部丢失，画像很稀。
2. **学习计划「答对才算完成」。** prompt 和工具描述反复要求「讲完不算完成，需要作答时设 awaiting_learner 并停下，答对才标 done」。模型因此习惯「讲一点、停下考你、等你答」，回复变得套路化、计划常常卡住。

此外，后台复盘每个对话要攒满 10 轮才触发，大多数对话到不了 10 轮，USER 笔记几乎得不到更新。

方向参照 Hermes：信任模型去理解用户，靠透明（用户看得见、改得了）和容量约束来治理，不靠证据门槛。

## 任务 A：学习观察允许「推断」，复盘更频繁（后端）

**分支** `feat/memory-inferred-observations`

**负责的文件**（A 独占，B、C 不碰）
- `backend/app/chat/agent.py`：只改 `ANALYSIS_PROMPT`（包括第 11 条 plan_updates 规则）、`validate_analysis` 里 observations 和 plan_updates 两段、`REVIEW_PROMPT`。不要改 `chat_messages`。
- `backend/app/chat/insights.py`：证据输出里加上 `source` 字段
- `backend/app/chat/schemas.py`：`MemoryEvidence.source`
- `backend/app/chat/store.py`：`record_observation` / `record_observation_changes` / `_record_locked` 及证据写入
- `backend/app/chat/service.py`：`_analyze` 里传 source 的地方，以及复盘触发阈值（`count >= 10` 和 `user_rows[-10]`）
- `backend/app/chat/cheatsheet.py`
- 对应测试

**数据约定（C 依赖这一条，不要改名）**
- `MemoryEvidence.source` 的取值由 `"message_quote" | "quiz_attempt"` 扩展为 `"message_quote" | "quiz_attempt" | "inferred"`。
- 对推断证据：`quote` 字段存「依据」（模型对行为的简短描述，200 字以内，不要求逐字出现在原文里），`message_id` 仍指向本轮用户消息，用于追溯。
- 数据库沿用 `learner_memory_evidence.source` 列，不新增列。

**改动**
1. `ANALYSIS_PROMPT`：observations 的每一项新增 `"source": "stated|inferred"`。
   - `stated`：用户亲口说的，`evidence` 仍须是最新消息里逐字、连续的片段（沿用现有规则）。
   - `inferred`：从最近几轮的表现里看出来的，`evidence` 写成一句「依据」，例如「连续两次把 i<=n 写成 i<n，都是边界条件出错」「看完例子后能独立写出，看定义时反复追问」。可以推断的有：反复出现的同类错误、独立正确完成、对某种讲法的明显反应、持续表现出的兴趣。
   - 仍然保留的判断：单纯提问或说「不懂」本身不是误区；「这次 / 这道题」类要求不是长期偏好；只有一次表现时不要推断成长期偏好。
   - 每轮上限从 2 条提到 3 条（`validate_analysis` 里的 `observations[:2]` 同步改）。
   - 改写时顺便把语气从「宁缺毋滥、必须、不得」改成说明理由，规则条数不要比现在多。
2. `validate_analysis`（observations 部分）：
   - `stated` 照旧要求 `quote_in(quote, user_text)`。
   - `inferred` 只要求依据非空、不超过 200 字，不做逐字校验。
   - 缺省 `source` 时按 `stated` 处理，兼容旧测试替身。
3. `store`：证据写入带上 source。推断证据的分量要低于原话。按 `_record_locked` 现有的状态和置信度规则实现，例如只有推断证据的记录不能直接进入「已掌握」，或者置信度增量减半，选一种并写测试。用户纠正过的记录（`user_corrected`）照旧不被推断证据覆盖。
4. `REVIEW_PROMPT`：
   - 允许把「在这些轮次里反复出现的」学习特点写进 USER。新增前缀「学习特点：」，写入时末尾标「（推断）」，例如「学习特点：看具体例子比看定义理解得快（推断）」。
   - 用户明确说过的照旧不加标记。
   - 仍然禁止从单次行为推断。
   - 知识点的掌握和误区仍然不写进 USER，它们在 learner_memories 里。
5. 复盘阈值：每个对话 10 轮改为 4 轮（抽成模块常量，例如 `REVIEW_EVERY_TURNS = 4`），复盘取最近 4 个计数轮次。
6. `cheatsheet.py`：考前一页纸的「易错红榜（带原话）」只引用 `source != "inferred"` 的原话；只有推断证据的记录显示 summary，不要把依据当成原话加引号。
7. `insights.py`：返回给前端的每条证据都带上 `source`。前端靠它区分原话和推断，C 依赖这一条。
8. 学习计划的后台判定，按任务 B 的新语义改写。任务 B 不碰 `agent.py`，这一条由 A 负责：
   - `ANALYSIS_PROMPT` 第 11 条：`plan_updates` 可以把 `awaiting_learner` 的步骤标为 done，前提是最新消息表明用户已经给出了需要的信息或回答，或者明确表示懂了、要继续。不再要求「独立答对」。
   - `validate_analysis` 的 plan_updates 段：去掉 `quote_in` 逐字校验；仍然只允许处理 `awaiting_learner` 的步骤，`evidence` 保留为非空短句，用于记录。

**测试至少覆盖**
- inferred 观察在依据不出现在原文里时也能入库，source 记为 inferred。
- stated 观察对不上原文时照旧丢弃。
- 只有推断证据的记录不会被直接判为已掌握（或按你选的规则断言）。
- 第 4 个计数轮触发复盘。
- cheatsheet 不把推断依据当原话。

## 任务 B：学习计划去掉「答对才算完成」的门槛（后端 prompt 与工具描述）

**负责的文件**（B 独占）

- `backend/app/agent_tools/__init__.py`：只改 `update_plan` 的 description。
- 注意：对话结束后的后台分析（`agent.py` 的 `ANALYSIS_PROMPT` 第 11 条和 plan_updates 校验）也有「答对才完成」的门槛。这部分由任务 A 改，B 不要碰，也不用等 A。

- 对应测试（`test_learning_plan.py`、`test_guidance.py`、`test_coordinator_wakeup.py`、`test_quizzes.py` 中涉及的断言）

**新语义**
- 计划是用来跟踪进度的，不是用来考用户的。
- 一步的内容讲完、用户没有表示没懂，就可以标 done；用户说「懂了」「下一步」「跳过」也可以直接推进。
- `awaiting_learner` 只在确实需要用户提供信息、做决定，或者用户自己要练习、自测时使用。不要为了检验理解而停下来出题。
- 要不要穿插小测，看 `teaching_preferences` 和 USER 画像。用户偏好被提问时可以出题，但出题不是推进的前提。
- 保留：同时最多一个 in_progress；不能回退 done；不预填完成进度（没讲到的步骤不能标 done）。

**改动**
1. 上面列出的 prompt 和工具描述，按新语义重写相关句子。删掉「讲完不等于学会」「答对后才标 done」「AI 讲完不算完成」这类表述。篇幅不要变长。
2. `micro_quiz` 的 `planStepId` 机制保留不动（`WIDGET_SCHEMA_GUIDE` 里那句也不改）：用户在卡片里答对时仍会自动完成对应步骤，只是它不再是唯一的完成方式。
3. `plan.py` 里「进入等待后尚无学习者新消息」的拦截（`awaiting_learner → done` 必须等用户新消息）：评估后二选一。
   - 保留：同一轮里先设等待、又标完成本身就不合理。
   - 改为允许：如果你认为它会让计划卡住。
   - 无论选哪个，都在报告里写明理由和对应测试。其他校验不动。

**测试至少覆盖**
- 讲解类计划可以从 in_progress 直接到 done，不需要经过 awaiting_learner。
- 「不能回退 done」「最多一个 in_progress」仍然生效。
- prompt 文本断言随新语义更新（注意 `test_chat_general_assistant.py` 里 chat 角色的断言不要动）。
