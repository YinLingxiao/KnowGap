# 后端 B6 · 多智能体学习规划 · 规格

对应文件：`.codeartsdoer/specs/learning_plan_draft/spec.md`、`design.md`、`tasks.md`

## 一、目标
1. 在学习空间内从当前学生的未解决误区生成复习任务草稿。
2. 诊断、规划、审核三个智能体严格串行，返回草稿及各自结构化输出。
3. 每条最终任务必须可追溯到一个诊断选中的 `memory_id`，并具有明确时长。
4. 草稿生成只保存待确认数据，不写日程；用户确认后才写入选中任务。
5. 审核由确定性代码规则兜底，模型不可用时仍能返回符合硬约束的结果。
6. 不修改 `chat/store.py`、前端、既有日程拆解及公开日程来源枚举。

## 二、验收原文
> 验收照任务单：三个智能体顺序对、每条草稿有依据和时长、生成不写日程、确认才写、重复和超时长被拦、日志可见、原有测试全绿。测试用假模型队列喂三段 JSON，caplog 查日志。

## 三、实现方案

### 3.1 模块与表结构

- 新增 `app/learning/` 的 `schemas.py`、`agents.py`、`service.py`、`router.py`。
- 新增三份 `app/learning/prompts/zh/*.yaml`，由现有 PromptManager 加载。
- `main.py` 只增加学习路由导入和挂载，注入现有聊天模型对象。
- `learning_plan_drafts` 保存草稿标识、学生、空间、日期、预算、三阶段 JSON 和创建时间。
- `learning_plan_draft_tasks` 保存最终任务快照、执行顺序和可空的 `confirmed_task_id`。
- 任务表以 `(draft_id, draft_task_id)` 为主键，以 `(draft_id, task_order)` 唯一。
- 使用 agenda 风格的 `ensure` 和 `CREATE TABLE IF NOT EXISTS`，复用当前 SQLite。

### 3.2 两个接口

- `POST /api/learning/plans/draft`
  - 入参为 `subject_id`、严格整数 `budget_minutes`（1～120）、不早于今天的 `deadline`。
  - 短连接读取空间、全部未解决误区和证据，关闭连接后再串行调用三个智能体。
  - 返回 `draft_id`、最终 `tasks` 和固定顺序的三条 `agents` 执行记录。
  - 只写学习草稿表，不调用日程初始化或插入路径。
- `POST /api/learning/plans/{draft_id}/confirm`
  - 入参只有 `task_ids`，禁止客户端提交任务内容字段。
  - 按 `draft_id + student_id` 读取草稿，仅处理属于最终快照的选中标识。
  - 从服务端快照写入日程，固定 `source=learning_agent`，保留 `memory_id` 和 `duration_minutes`。
  - 同一 `BEGIN IMMEDIATE` 事务完成插入与确认标记回填，重复选择不重复创建。

### 3.3 三阶段与审核规则

- 诊断：只选择候选误区，服务端用快照覆盖主题和摘要，重复诊断保留首项。
- 规划：服务端生成草稿任务标识，按 `due`、`priority`、原顺序排序并连续编号。
- 依据：非空 `memory_id/evidence`，标识属于诊断集合，依据含完整标识及具体理由。
- 字段：标题为 1～200 字；单条时长为 5～120 的严格整数。
- 去重：相同 `memory_id` 只保留顺序最靠前的合格候选，其余记 `duplicate`。
- 日期：计划日期位于今天与截止日闭区间，缺失、无效或越界均拒绝，不自动裁剪。
- 预算：保留最长合格前缀；首次超限后，当前及后续任务均记 `over_budget`，不补入短任务。
- 模型审核：不得恢复规则拒绝项，只能追加拒绝；最终通过集合和总时长由服务端重算。
- 降级：审核异常、超时或结构无效时使用完整规则结果，不返回 503，不重试。

### 3.4 日志与连接边界

- 每个实际启动阶段写一条 `event=start/status=running` 和一条结束日志。
- 结束状态为 `success`、`failed` 或 `rule_fallback`，日志包含阶段名和 `draft_id`。
- 成功链路恰好六条边界日志；诊断或规划失败不伪造后续阶段日志。
- 模型调用期间不持有数据库连接或事务，保存草稿与确认分别使用新的短事务。
